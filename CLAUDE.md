# canvas-particles-space

A WebGL particle flight through space, ending in a black hole. React only drives the UI. The scene itself runs in one requestAnimationFrame loop.

## Working here

- **Work in a worktree of your own.** Several agents work on this repository at once, in the main checkout among others. A task that changes files starts with `git worktree add ../canvas-particles-space-<task> -b <branch> master` and `pnpm install --offline --frozen-lockfile` there (a few seconds from pnpm's store), builds into that worktree's `dist/`, and previews films with `node .claude/skills/space-scene/scripts/space.mjs` run from it (the `space` MCP server serves the `dist/` of the checkout the session started in). When its checks are done (Checking a change), rebase on master and fast-forward master to it (`git -C <main checkout> merge --ff-only <branch>`), run `pnpm build` in the main checkout, whose `dist/` is what the `space` server and a local preview show, then remove the worktree, taking `node_modules` out first: it is full of junctions, and a removal that walks one empties the folder it points at.
- **A brief for another agent points here**, at `docs/` and at `scripts/bench.mjs`; the agent reads them itself, so the brief states the goal and what is particular to the task. Its checks are the ones Checking a change gives for its kind.
- **A commit message** is a subject line of what changed, then a few short paragraphs: why, and how it was checked, with the numbers that decided something.

## Checking a change

A change owes the checks of its kind, each run once, on the finished change. What each one answers goes into the commit message as printed.

| The change | Owes |
|---|---|
| Any | `pnpm build` and `pnpm lint`, both clean |
| Adds, renames or removes a setting, an intro parameter, a layer or a preset | the audit (Driving the scene), printing no problem |
| Adds work to the per-frame path: per particle, per pixel, a loop, an allocation | Measuring. A knob read once a frame and a uniform in place of a constant add none |
| Touches only `films/` or docs: a film, a reel, a script, a voice-over, a rule | nothing more, since no code a bench measures has changed |

- **The verdict closes the measurement.** `bench.mjs` ends in a line that begins `VERDICT`. On `within noise` it is done: the script has already repeated the runs whose ranges were apart, so the same call again brings no new fact. `apart` with the change slower is a finding, and Measuring says what to do with it.
- **The films' bytes are compared at the user's word.** `node scripts/bench.mjs films --against <commit>` tells whether the previews of `films/` moved between two builds. It runs only when the user asks which change moved a picture; no change owes it.
- **After a rebase on a master that moved**: build, lint and the audit again, then fast-forward at once. The frame time was measured against the change's own parent and still holds.
- **Checks take turns across the machine.** The commands of `bench.mjs` and the film server's previews and renders wait for one another (`scripts/turn.mjs`), since a build measured beside another agent's Chrome measures that agent. `waiting for ...` is that turn. A new script that drives Chrome takes it too. A bench holds the turn for its whole run, minutes long, so it starts once the task's previews are done, and a preview's output is read unfiltered, so its `waiting for ...` is seen.

## Devices

Write for current browsers with WebGL2 on desktop-class hardware: one code path, defaults tuned for that hardware, and frame time judged by Measuring on the development machine. Legacy browsers and weak devices are not supported, and that is a hard rule: no fallback, polyfill, lighter mode, lowered default or feature turned off for them, and no change is held back or reshaped by what it would cost on them.

## Earlier films

The scene is built for the film made next: a change takes the laws, the defaults and the look that are right today, and the films in `films/` are drawn by them from then on. The picture a film had before is not kept, and that is a hard rule: no flag, preset, mode or default holds an earlier look, and no change is held back or reshaped by the films it redraws, or counts them as its cost in a plan or a report. A hook holds it (`.claude/hooks/earlier_films.mjs`, whose header says what it reads): an answer, a file's text or a commit message that keeps or prices an earlier look is sent back.

## UX

Every panel reads well at its defaults and still lets the user change layout and look. Judge every UI change by readability, compactness and clarity first.

- **A section's rarely moved settings sit in its Fine Tuning group** (`SettingsFine` in `settings_section.tsx`), closed by default and one click further in, so the section reads at its defaults as it did without them. A knob for a number that was a constant in the code goes there, in the section of its effect; the settings that set an effect stay in the section itself. A track of the intro debugger has the same group: the parameters in its `fine` list (`INTRO_TRACKS`), drawn by `TrackFine` in `intro_track_list.tsx`.
- **Microcopy is one short line.** A control's hint fits one line of the 340px panel (at most 42 characters): what the control changes, in plain words, with the direction when it is not obvious ("Higher: shorter trails"). The full explanation goes in the spec's `description`, which the agent API reads; the context menu shows the spec's `hint`.
- **A hint lives in the control's context menu** (`hint_menu.tsx`, one menu for the page), the one place a panel shows it: a right-click, Shift+F10 or the Menu key, or a long press on touch opens it with the control's name, its hint and, where it has a default, a reset to it. A row offers its hint through `data-hint`, `data-hint-label` and `data-hint-reset`, and keeps the same text as an `sr-only` line tied to its control with `aria-describedby`, so screen readers always read it. Panels draw no hint lines, help icons or HELP toggle.
- **A panel opens and closes from one place**: its button in the scene toolbar at the top right (`control_panel.tsx`), which never moves or hides and shows the panel open with `aria-expanded` and a solid fill; panels have no close buttons of their own. Opening moves the focus into the panel; Escape closes the panel the focus is in; closing with the focus inside returns it to the panel's button.
- **A slider's label and value sit on a quiet tint** with a solid edge at the value, never on a strong fill or a blend mode. Every value carries its unit, formatted once in the spec (`format` in `simulation_specs.ts`, `unit` in `INTRO_PARAM_SPECS`) and spoken through `aria-valuetext`.
- **What the pointer does to the camera, the keyboard does too.** The scene is a Tab stop with a visible focus edge, and while it has the focus the arrows, plus, minus and Home move the camera through the sliders' own ranges, steps and names (`src/lib/camera_keys.ts`); a screen reader hears where the camera now is from the status line beside the canvas, and the hints at the bottom show the keys while the keyboard holds the scene. A new way to move the camera with the pointer gets its key there.
- **Scrolling never changes a value**: the wheel moves a slider only while it has the focus or with Shift or Alt, and a finger moves it only after a sideways slop or with a short tap, never one that lands while the panel scrolls.

## Render performance

The hard constraint in this project is frame time. Any change that touches the **per-frame path** has to keep it lean. The per-frame path is:
- `renderFrame` in `src/components/particle_canvas.tsx`
- `advance` in `src/lib/scene.ts`
- the step of the particle field: the vertex shader of `src/lib/field_step.ts`, which `src/lib/field_feedback.ts` runs once a frame for every particle
- `render` in `src/lib/particle_renderer.ts`
- the composite fragment shader in `src/lib/webgl_shaders.ts`

The main thread only gathers a frame's numbers: no loop over the particles runs in JavaScript, and none is to be brought back. What costs per particle is the step's shader and the stroke it draws, multiplied by the particle count (24 000 by default, 200 000 at most); what costs per pixel is the composite pass.

Two words used here and in `docs/`:
- **Gated**: the code runs only while its uniform or flag is non-zero and costs nothing otherwise; in a shader, `if (u_<effect> > 0.0)` with the uniform 0 while the effect is off.
- **Deterministic**: one seed and one film draw the same bytes every time on one machine. The field is stepped by the graphics card, and another card or driver may round a sine or a square root differently.

### Frame pipeline

1. `renderFrame` reads both stores with `getState()`, applies the frame-rate cap through the `nextFrameSlot` scheduler, derives `frameScale` from the real elapsed time and hands both stores to the scene as its `SceneInput`. `advance` assembles the frame from that input alone.
2. `render` steps the particle field on the graphics card: the step's vertex shader reads each particle's record from one buffer and transform feedback writes the next into a second (20 floats: its state, the clipped stroke it draws this frame, whose opacity's sign is the side of the black holes it is on, the light it leaves in the photon ring). The main thread hands over the step's numbers as uniforms and sends up only the newborn, when the field grows.
3. `render` reads the strokes straight from that buffer and draws instanced quads into a persistent scene FBO that holds the trails, and the orbits' traces, the lattice and the flows into a layer of lines drawn anew. In 3D, while something can stand in front of the black holes, a second persistent FBO and a second layer of lines are bound beside the first, and the same draws write each stroke into the one on its side of the holes. It then runs one full-screen composite pass for the lens, the intro effects and the title, which lays the front layers over the holes, and draws the space sheet over it while that is on.

### Invariants

- **The scene reads no store, no window and no clock.** `createScene` owns the field, the black hole, the intro frame and the renderer; a frame depends only on its `SceneInput` (settings, intro parameters, hidden layers, reduced motion) with `frameScale` and `dt`. The page keeps the loop, the frame-rate cap, input handling and every store write. Random numbers come from the scene's seeded generator (`src/lib/random.ts`), never `Math.random`, and the field's step draws its own from the particle's number, the step's number and the seed (`chance` in `field_step.ts`), so one seed and one sequence of inputs draw the same frames, which is what lets a film render the scene in a plain loop.
- **The per-frame path allocates nothing.** `frame`, `settings` and `composite` are created once with the scene, the page's `input` once in the effect, and all are mutated in place. New per-frame data becomes fields on these objects or preallocated typed arrays, and no closure is made per frame.
- **React never renders per frame.** The loop reads stores through `getState()`. It writes to a store only when a value changes, and only at a throttled rate:
  - `measuredFps`: every 500 ms;
  - the debugger readout: every 66 ms, and only while the debugger is open.

  Every `set()` also wakes every subscriber, including `syncLoop` in the canvas.
- **Fast-changing values stay in leaf components.** A component that shows `readout` or `measuredFps` subscribes to just that value through a narrow selector (`MeasuredFps`; in the debugger `TimeReadout`, `Ruler`, `Playhead`, `TrackValue`, `SpanBar`, `MarkerButton`). Large components (`IntroDebugger`, `IntroTrackList`, `TrackRow`, `ControlPanel`) never subscribe to them.
- **The field is the graphics card's.** A particle's state lives in a buffer there and nothing of it is read back. The scene makes a particle only when the field grows (`spawnParticle`, sent up once, `fieldBorn`); after that the step's shader moves it, takes it at a horizon, makes it anew and draws its random numbers (`chance`). A new per-particle value is a float of the record (`FIELD_FLOATS`, `FIELD_VARYINGS` and the offsets in `field_step.ts`, `send` in `field_feedback.ts`). A new numeric step setting is a name in `STEP_KEYS` there, read in the shader as `s_<name>`, with its resting value in `createStepSettings`. What a particle leaves for the rest of the scene goes out as the ring's light does: a value of its record that a pass adds into a texture (`lightRing`), never a read-back.
- **Particles keep what speed Inertia lets them.** A push of the holes (pull, Orbital Force, the spin's drag, the second hole) moves a particle at once and, while Inertia is above 0, also adds to its sideways speed (`vx`, `vy`), which carries it on at that share per 60 Hz frame; a new force on the particles is such a push.
- **3D is a second step, not a branch in the first.** `stepSpace` (`src/lib/field_step.ts`) steps the same field with the laws of `stepFlat` in space: the holes are points (`holeWorldX`..`companionWorldZ`), gravity follows the true distance and ends at the sphere of Gravity Reach, the horizon is a sphere (`respawnBeyondSphere`), the spin's drag turns space about the axis as it stands in the scene, Orbital Force swirls about an axis `advance` hands over (`swirlX`..`swirlZ`: the line of flight, turned to the spin's axis by Swirl Follows Spin), the opening reveals a sphere round the blast's place (`fromBlast`), and Inertia keeps speed along all three axes (`vz` as well). The shader picks one by `threeD`, so a new law of the particles goes into both. Each particle is seen through two poses of the camera (`cameraPose` in `src/lib/camera_pose.ts`: its circle round the hole, then its move, its head and its roll): the frame before's where its stroke starts, this frame's where it ends, and a turn of more than the `cameraCutTurn` setting in a frame, or a move past `cameraCutShift`, starts the trails afresh. Its brightness is judged by its own move, both ends seen through this frame's pose (`own`), so a camera that turns streaks the trails and lights nothing. The circle places things in the scene; only the pose sees them. Straight on it draws what the flat step draws.
- **In 3D the rest of the scene turns with a few numbers a frame.** The holes, the pair's centre, the blast and a swallowed star's flare are places of the scene: `advance` projects each (`look`), draws the holes at their apparent size (`holeScale`), and whatever is laid on the screen reads where they are seen. Two holes at different depths are seen through each other (`u_pairDepth`, `companionBend`): the nearer bends the light of the farther, and its shadow hides the farther one's ring. Spin Tilt and Spin Axis are seen straight on, so in 3D the axis stands in the scene: the shadow, the lens and the ring see it turned by the camera, the particles and the orbiting stars feel it as it stands. The orbiting stars and the flows are places of the scene that their vertex shaders turn with the camera's three columns (`u_turnX`, `u_turnY`, `u_turnZ`), the sky is read where the bent ray points, through the camera's turn (`u_turnRight`, `u_turnDown`, `u_turnAhead`, no turn in the flat mode): the stars and the nebula on a sphere round the camera (`sphereStar`, `nebulaSphere`), even in every direction, the Lensed Grid on the faces of a box (`skyFace`), and the flat mode's backdrop turns into the sphere by the share the camera has eased in (`u_skySphere`), both worked out only between 0 and 1 ( the tint of the particles takes the line of flight from the same turn, `u_flight`), and the sheet is a surface of the scene, the main hole's equator (`equator` in `advance`) lifted along the way it faces by the depth of the well, so the well's bottom stands at the hole, seen through the camera's own pose as the particles are (`laySpaceSheet`): from the side, from below, near and moving, with nothing held back.
- **What stands in front of the holes is drawn in front.** In 3D `advance` hands the step the nearer hole's distance from the camera (`frontAway`, 0 in the flat mode, whose law takes whatever covers the hole at any depth, with no hole and with a hole behind the camera), and a stroke whose middle is nearer than that writes its opacity below 0 (`stroke` in `field_step.ts`); something between two holes is behind the nearer alone, and is the lens's only where that hole's lens reaches it on the picture (`frontReach`, each hole's own distance in `holeFront`, `companionFront`), since the layer behind is read through both lenses and would bend the farther hole's own matter by its own lens. The boundary is a band, not a plane: over Front Depth (`frontDepth`) behind the hole the share seen through the lens grows as a thin lens's bend does, and what is seen within a shadow there is the lens's (`BEHIND_GLSL`, one text for the step and the line shaders); a particle of the field or a flow goes wholly to one side past a share of its own (`ownShare`), a trace or a lattice line into both layers at their shares. The renderer then binds the scene texture and the front scene texture side by side (`sceneBoth`) and fades and stamps both in one draw each: the stroke fragment shader writes two targets, a stroke into the one its vertex shader names (`v_front`) and nothing into the other, which the brighter-of-two blend leaves as it was. The orbit, lattice and flow vertex shaders take their side from their own depth (`SIDE_GLSL`, `u_side`) and are drawn once into the two layers of lines (`linesBoth`). A new thing drawn in strokes goes through the same fragment shader and names its side; drawing a buffer once for each side costs the vertex work twice, which was 13% to 28% of the frame rate with the orbiting stars, 200 000 particles or the flows on. The composite pass reads the front layers where the pixel is (`layerPoint(frag)`), not along the bent ray, after the shadows, the lenses and the rings, behind `u_front`; the camera's zoom, jolt, lens fringe, exposure and the film act on them, the holes' waves, absorption and bends do not. The sheet keeps a piece nearer than the holes uncleared (`v_front`). A new thing drawn round the holes in 3D takes its side the same way.
- **Motion is frame-rate independent.** Per-frame motion is scaled by `frameScale` (relative to 60 Hz, capped at 6); seconds-based motion uses `dt`; `src/lib/frame_pacing.ts` treats a one-off stall as a normal frame. Trails fade in whole 60 Hz steps through `fadeBacklog`. A particle is a disc sweeping a round-capped capsule over a frame, stamped with the brighter-of-two blend (`MAX`), never added; its brightness comes from its own speed on the screen per 60 Hz frame, worked out in the step (`s_speedGlow` bends that, `s_frameScale` keeps it the same at any refresh rate), and a particle that did not move writes no stroke. Gravity is never scaled by the flight speed, so at Base Speed 0 only the particles gravity moves stay lit.
- **The composite shader is gated effect by effect.** It runs for every device pixel on every frame, so each effect sits behind its uniform; after the intro only the lens, the shadow, the ring, the background stars and, in 3D, the front layers (`u_front`) do work. A new effect is gated the same way. The Ray Traced lens (`u_trace.x`) is the one that works every pixel (`traceSweep`); the main thread only places its camera (`cameraFor` in `src/lib/lens_trace.ts`, redone only when Einstein Radius changes). A spinning hole (`u_spin.x` above 0) takes the Kerr ray (`kerrRay`, or `kerrRayFrom` where the sines and cosines are at hand, in `src/lib/kerr_glsl.ts`; its reference is `src/lib/kerr_trace.ts`), and its shadow and ring follow the outline `updateShadowShape` works out when spin, tilt or the camera change. The Horizon Grid (`u_horizonGrid.x`) follows the rays of the shadow back to the horizon (`kerrHorizonFrom`, three rays a pixel there, for the width of its lines). The GPU's `asin` and `sin` lose near-equal differences, so take such a quantity (the ray's remaining fall) from an identity, never by subtracting.
- **Opening Settings builds nothing.** `SettingsBody` is built once with the page, before the first frame, in a detached element the open panel attaches; keep that work there, since a long task while the scene runs makes the next frame jump. A closed section stays mounted and hidden, every toggle is a leaf bound to its own setting, each slider subscribes to its own setting through `SettingSlider`, and `settings_persistence.ts` writes to the browser in idle time.
- **The space grid costs the main thread a few numbers per frame.** The Lensed Grid is a block of the composite shader gated by `u_skyGrid`, read at the bent ray like the stars. The Sheet (`src/lib/space_grid.ts`) is a static buffer of line pieces that the grid vertex shader places, dents (`dent`, whose physics its comment gives) and ripples, in one instanced draw over the finished frame while Sheet is above 0, clearing its lines round each shadow except a piece nearer the camera than the holes; with Sheet Rings above 0 the same buffer is drawn as rings at equal steps of the well's depth and spokes across them (`u_rings`). `placeSheet` lays out the surface and the pose it is seen through, a few numbers a frame: the flat mode's own camera (`layFlatSheet`), the 3D camera's pose (`laySpaceSheet`), blended while 3D eases in; nothing about the sheet is computed per line in JavaScript. The Lattice (`src/lib/space_lattice.ts`) is the same law in three dimensions: a static buffer of line pieces, made when it is first shown, that its vertex shader draws in towards the holes (the same `dent`, one GLSL text for both) and sets before the camera, in one instanced draw into the orbits' layer, which the composite pass reads while `u_orbits` is 1, and a second into the front layer of lines while something can stand in front of the holes; only while Lattice is above 0.
- **Particles on the sheet are drawn there, never moved there.** With Particles on Sheet (`gridRide`) above 0 the particles are the sheet's vectors: each stroke lies on its surface and shows where matter, or space, goes on it. A particle within Ride Depth (`gridRideDepth`) of the main hole's equator is dropped onto that plane along the way it faces, and the point of the surface over it is seen through the sheet's pose; the ride share, falling to 0 at the slab's edge, blends the two places in the scene before they are seen (`laidOn`). The step's shader does it in `stroke`, for `stepFlat` and `stepSpace` alike, behind `u_ride.x`, and the flow vertex shader from a flow's place in the scene; the particles' laws know nothing of it. The sheet's surface and its projection are one GLSL text, `SHEET_GLSL` in `src/lib/webgl_shaders.ts` (`sheetDepth`, `sheetSeen`, `sheetScreen`), which the grid program, the step (`RIDE_GLSL`) and the flows all read, with the numbers `sendSheet` hands each; a change to how the sheet is placed, dented or seen goes there once. The step reads the sheet through `StepSettings.sheet`, so `advance` lays it out (`placeSheet`) before the particles are stepped, drawn or not. Both ends of a stroke are seen through the sheet as it lies now: seen through the sheet of the frame before, a camera that moves would draw every slow particle as a long line.
- **A flow has no state.** The flows (`src/lib/flows.ts`) are particles told where to go, three bands round the main hole, each in the hole's equator (`equator` in `advance`) tipped by its own tilt. Where a particle stands, in its flow's plane and the height above it, is worked out in the flow vertex shader (`placeAt`) from its own four numbers in a static buffer and the flow's clock, and its trail is the stretch of the same path behind it, in pieces, drawn anew into the orbits' layer in one instanced draw for each flow whose brightness is above 0 (and a second into the front layer of lines while something can stand in front of the holes), and only on a frame that is shown. `stepFlow` and `turnFlow`, which hands the shader where the camera sends the flow's three directions (`u_turnX`, `u_turnY`, `u_turnZ`), are the few numbers a frame a flow costs the main thread. Nothing of a flow's particle is kept from one frame to the next or computed in JavaScript, so a new motion of a flow is a line of `placeAt` and a uniform, never a per-particle array. With Particles on Sheet a flow is laid on the sheet in that shader (`RIDE_GLSL`, which the field's step lays its strokes with too). A flow that ends inside the horizon feeds the ring by `feedRing`, a loop over the ring's bins, gated like the rest. With Particles off (`fieldEnabled`) the field is neither stepped nor drawn.
- **A second black hole is gated.** `stepPair` (`src/lib/companion.ts`) is a few numbers per frame, the pair's motion in its own plane; `advance` sets the two in the scene with that plane's directions (`pairPlane` in `scene.ts`, from Orbit Tilt and Tilt Toward), in both modes, and the flat mode draws them as they lie across the screen; the field's step takes the companion's capture and pull in one block behind `s_companionRadius`; its lens, shadow, ring and spiral wave sit behind `u_companion.z` and `u_pairWave.x`, and the sheet takes its second well and wave from uniforms. The merger is the pair's own motion: `stepPair` gives the merged hole's tone and the pair's last angle, and `advance` turns them into `u_holeOval` and a wave that the intro's wave block draws through `u_gravityWaveCenter`, `u_gravityWaveTurn` and `u_pairFront`; the opening's ringdown and a fired one stand still. Every gravitational wave moves the picture across its path, never along it, weakens as 1 over the distance (`waveReach`), and is seen as the slice through its source that faces the camera (`planeQuad`, which the ringing horizon's oval goes through too, in the plane `u_pairPlane` gives: the pair's orbit while there is one, else the plane across the line of flight); a new wave does all three. The hole a merger leaves spins about the orbit's axis.
- **Uniforms go through the dirty-checked setters** `setUniform1f`, `setUniform2f`, `setUniform3f` and `setUniform4f` in the renderer, which skip unchanged values. The texture units are fixed: the scene on 0, the title on 1, the photon ring's energy (`src/lib/ring_energy.ts`) on 2, the orbiting stars' traces on 3, a spinning hole's shadow outline (`src/lib/kerr_shadow.ts`) on 4, the light the field leaves in the photon ring (`src/lib/field_feedback.ts`) on 5, the field's trails in front of the black holes on 6, the lines in front of them on 7.
- **The camera's zoom redraws, it does not magnify.** A zoom above 1 (the Zoom setting, the intro's camera) is applied to the geometry: the particle and orbit vertex shaders draw at `u_zoom`, and the composite pass reads the layers through `u_layerZoom`, the zoom they were drawn at. Every edge and hairline in that pass is measured in `px`, the scene pixels under one screen pixel, so nothing softens or thickens with the zoom; a new shape there follows the same rule. A zoom below 1 is left to the composite pass. The camera pans by moving the point its zoom leaves in place (`zoomX`, `zoomY` in `advance`), kept inside the frame, with nothing new in any shader; whatever places things on the screen (captions, the sheet, `scene.holeShiftX`) reads that point. A stroke starts where the particle stood in the last frame's picture (`u_zoomFrom`), so a moving camera streaks the trails and a camera cut (a jump past the `cameraCutZoom` or `cameraCutShift` setting in one frame) starts them afresh. The title sprite and the intro's dust still soften when magnified.
- **Orbiting stars leave lines, not a picture.** `stepOrbiters` (`src/lib/orbiters.ts`) integrates at most 64 stars in the scene's three coordinates, each born in the hole's `equator` tipped about a node of its own and then moved by its motion alone, so a spin axis that turns later precesses its orbit; the spin acts on it as the gravitomagnetic field of a spinning mass about the axis as it stands in the scene, in the sense the field's particles are dragged. It hands the renderer one row a frame (a new one every `STRETCH_SECONDS`, three numbers a point), which goes up in one `bufferSubData` into a ring of rows on the GPU; the orbit program draws the whole layer anew each frame around the hole at the camera's zoom, turned by the camera's three columns (`u_turnX`, `u_turnY`, `u_turnZ`) in 3D and straight on in the flat mode, and the composite pass reads it only while `u_orbits` is 1. How a trace ages (`dimmed`) is told in `orbiters.ts`.
- **GPU buffers grow and are reused.** The field's two buffers grow ×1.5 and carry over what they hold (`reserve` in `field_feedback.ts`); the orbits' rows are refilled with `bufferSubData`. The resolution follows `PIXEL_BUDGET` (4.5 M device pixels), with `MAX_PIXEL_RATIO` 2.
- **Resize is coalesced into one rAF.** World coordinates do not depend on the viewport, so a resize reallocates only GPU targets and keeps the particle field.
- **The loop runs only while it is visible.** `syncLoop` stops it while the scene is paused, while the tab is hidden and while the WebGL context is lost. Every GL resource is created inside `createParticleRenderer`, so `webglcontextrestored` rebuilds it all. A new texture or buffer belongs there.
- **The scene needs WebGL2.** A browser without it gets the message in `particle_canvas.tsx` instead of the scene, and the renderer calls WebGL2 directly (Devices). The composite pass and the sheet are GLSL ES 1.00, which WebGL2 compiles as it is; the field's step and the passes of the ring's light are GLSL ES 3.00, which transform feedback asks for, and so are the programs that fade and stamp strokes, which write two targets in one draw (their vertex shaders are written as the others are and read as 3.00 through `MODERN_VERTEX`).

### Measuring

A change that adds work to the per-frame path is done when `bench.mjs` says its main-thread time per frame is `within noise` of the commit before it. Runs vary by about ±10%, so the script takes two runs of each build in turns and as many again when their ranges come out apart; one call is the whole measurement. `apart` with the change slower is a regression: find where the time goes, or, when it is the price of a visual feature, report it in numbers.

- **Throughput**: `node scripts/bench.mjs page --against <commit>` builds the commit before your change (`HEAD` while the change is uncommitted, else its parent) in a temporary worktree, builds this checkout, and measures both in turns; `--debug` measures with the intro debugger open, for a change to the debugger. The default scene is flat with every other layer off, so a change to what 3D, the flows, the orbiting stars, a pair, the grids or the nebula draw is measured with `--set '<json>'`, the settings of a scene that shows it (`window.space.set` takes them once the opening has ended); the frame rate each run prints is read with the verdict. To find where the time goes, take a CDP `Profiler` capture with self time per function.
- **The graphics card's share**: the field's step, the strokes and the composite pass run on the graphics card, and the main thread's time does not show them. Each run prints the frame rate beside it: a change to a shader that works per particle or per pixel is read there too.

For orientation, with the field stepped on the graphics card, on the development machine (RTX 3070):

|---|---|---|
| Default | 2220–2330 | 0.42–0.44 ms/frame |
| `?debug`, debugger open | 715–960 | 0.53–0.56 ms/frame |

## Driving the scene as an agent

`window.space` (`src/lib/scene_api.ts`) reads and changes every simulation setting and intro parameter and drives the intro timeline. It loads in development, and on a deployed build only with `?agent`, as a chunk other visitors never download. To drive the page or make a film, use the `space-scene` skill.

- **Each fact has one home**: ranges and meanings in the specs (read through `describe`), the page's commands in `help()`, the film format in `FILM_GUIDE`, how to use the knobs in the skill, the rules for the code here and in `docs/`. A simulation slider is described once in `src/lib/simulation_specs.ts` (the Settings panel builds from it), an intro parameter in `INTRO_PARAM_SPECS`; a new setting goes there, with its default in `particle_store.ts`, its key in `SIMULATION_SETTING_KEYS` and its row in `settings_body.tsx` (a slider sets its own field and needs no setter), and the panel, the agent API and films pick it up. A colour is a setting of its own kind: a `'#rrggbb'` string in the store, its key in `SIMULATION_SETTING_KEYS`, its spec in `SIMULATION_COLOR_SPECS` beside the sliders', a `SettingColor` row in the panel, and `readSceneColor` (`src/lib/scene_color.ts`) where the scene reads it; the agent API, films, scripts and the audit take it from its spec. A setting that is neither a slider nor a colour also needs a line in `parseSettings` (`src/lib/agent_values.ts`) and, to move along a film's track, one in `readTracks` (`src/lib/film.ts`).
- **A number that shapes the picture is a knob.** Agents make films from the knobs alone: what a film cannot set, it cannot show. A change that brings a strength, a falloff, a reach, a rate, a share or a colour gives each a spec whose default is the value you would have written into the code. Where physics gives the value, the knob is a multiple of it and 1 is the real thing (`frameDrag`). A knob read once a frame in `advance` is free; one that adds work per particle or per pixel goes through Measuring. The change is done when each of its numbers that shape the picture is a knob. What stays in the code is what frame time, memory or the precision of the arithmetic holds (a step count, the size of a buffer, a floor against a division by zero), with a comment that says so.
- **Every length around the black hole is in black hole radii**, so Black Hole Size alone scales the hole; a new length setting follows the same rule.
- **A change to the knobs ends with the audit.** After a setting, an intro parameter, a layer or a preset is added, renamed or removed, `node .claude/skills/space-scene/scripts/audit.mjs` must print no problem.
- **`public/index.md` is the door for agents from outside the page.** The build puts it into the page's HTML as markup inside `#root`, never as a `<noscript>` (`describePage` in `vite.config.ts` says why), the `<meta name="description">` in `index.html` says the same in one sentence, it answers a request with `Accept: text/markdown` (a route in `vercel.json`, not a rewrite, which would give way to the `index.html` at that address), and the page's `Link` header names it as its `service-doc`. It names commands and leaves every range to `describe()`, so change it only when a command it names changes, and change the canvas's label (`SCENE_LABEL` in `particle_canvas.tsx`), which names `?agent` and `help()`, with it. Preview deployments are behind Vercel's sign-in: check a change to the routes with the project's bypass secret in an `x-vercel-protection-bypass` header.
